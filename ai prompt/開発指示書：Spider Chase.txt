# 開発指示書：Spider Chase（仮称）

## 1. 開発目的

ブラウザ上で動作する、1対1のターン制鬼ごっこゲームを開発する。

ゲームの基本コンセプト：

- 蜘蛛の巣型のマップを自動生成する。
- マップ上にはキャラクターが待機できる位置（以下、ノード「●」）が複数存在する。
- ノード同士は通路（線）で接続されている。
- ユーザーとNPCが1対1で対戦する。
- ユーザーが先手で、ユーザーが1回移動するとNPCも1回移動する。
- ユーザーとNPCの役割によってNPCの行動アルゴリズムを変更する。
- ゴールへの到達、または相手の捕獲によって勝敗を決定する。
- マップと初期配置はランダムに生成する。
- ゲーム理論による探索を行い、初期配置で詰まないこと、指定された難易度を満たすことを検証する。

## 2. 開発環境・ファイル構成

### 使用技術

- HTML5
- CSS3
- JavaScript（標準機能のみ）
- SVG（マップ描画）

外部ライブラリ、外部画像、サーバー、データベース、API通信は使用しない。

ローカルPC上でHTMLファイルをブラウザで開くだけで動作すること。

### ファイル構成

初期バージョンは以下の1ファイル構成とする。

SpiderChase/
└── index.html

HTML、CSS、JavaScriptをすべてindex.htmlに記述する。

JavaScriptは機能ごとにクラスまたは関数を分け、セクションコメントを付けること。

将来の分割を容易にするため、以下の論理構造を維持する。

1. GraphGenerator
2. GraphValidator
3. PlacementGenerator
4. GameSolver
5. NPCController
6. GameController
7. Renderer
8. UIController

コードを短くするために、異なる機能を巨大な関数にまとめないこと。

## 3. ゲームルール

### 3-1. マップ

マップはグラフ G=(V,E) として管理する。

- V：ノード集合
- E：ノード間の接続集合
- 各ノードには一意のIDを割り当てる。
- 各ノードは2本以上の通路に接続する。
- 全ノードは相互に到達可能である。
- 通路は双方向移動可能とする。
- 1回の移動で隣接するノードへ1つ移動できる。

### 3-2. キャラクター

以下の3つを配置する。

- USER：ユーザー
- NPC：コンピューター操作キャラクター
- GOAL：ゴール

3つは必ず異なるノードに配置する。

### 3-3. ターン進行

基本的なターン順序：

1. ユーザーが隣接ノードを選択する。
2. ユーザーが移動する。
3. ユーザー側の勝利条件・捕獲条件を判定する。
4. NPCが移動する。
5. NPC側の勝利条件・捕獲条件を判定する。
6. 次のターンに進む。

ユーザーがゴールに到達した場合は、NPCの移動を待たずに勝利する。

捕獲は同一ノードに存在した場合とする。

通路上ですれ違っただけでは捕獲としない。

### 3-4. ゲームモード

モードA：ユーザーが逃走者

- ユーザーはゴールを目指す。
- NPCはユーザーを追跡する。
- ユーザーがゴールに到達すれば勝利。
- NPCがユーザーと同じノードに到達すれば敗北。

モードB：ユーザーが追跡者

- ユーザーはNPCを捕獲する。
- NPCはゴールを目指して逃走する。
- ユーザーがNPCと同じノードに到達すれば勝利。
- NPCがゴールに到達すれば敗北。

モードBでは、ユーザーの移動によって捕獲が成立した場合、NPCは移動できない。

## 4. マップ自動生成

### 4-1. 基本構造

極座標を使用した蜘蛛の巣型マップを生成する。

設定値：

- R：リング数
- S：放射方向数

基本ノード数：

N = R × S

ノードの識別：

v(r,s)

- r：リング番号
- s：放射方向番号

基本接続：

1. 同一リング上の隣接ノードを接続する。
2. 内側リングと外側リングを放射方向に接続する。
3. 一定確率で斜め方向の接続を追加する。
4. リングごとに角度や接続位置をランダムに変化させる。

中心部についてもノードの次数が2以上になるように構成する。

基本構造から追加接続を行う方式とし、単純な完全ランダムグラフは使用しない。

### 4-2. ランダム要素

以下をランダム化する。

- ノードの配置角度
- リング間の接続位置
- 斜め接続の有無
- 通路の密度
- 初期配置

ただし、見た目の座標変更とグラフ上の接続関係は分離して管理する。

### 4-3. グラフ検証

生成したマップについて以下を検証する。

- ノード数が指定数以上。
- 全ノードの次数が2以上。
- 全ノードが連結している。
- 自己ループが存在しない。
- 同じ通路が重複登録されていない。
- すべての通路が双方向になっている。

不合格なら再生成する。

将来的には関節点や橋の数も評価できるようにする。

## 5. 初期配置

USER、NPC、GOALをランダムに配置する。

配置時には以下を考慮する。

- USERとNPCは別ノード。
- GOALはUSERとNPCとは別ノード。
- USERとGOALの距離が極端に近くならない。
- USERとNPCの距離が極端に近くならない。
- ゴールへの経路が存在する。

単純なランダム配置だけで採用せず、後述のGameSolverで検証する。

## 6. ゲーム理論による勝利可能性の検証

本ゲームの重要機能。

単純な最短経路探索だけで難易度を決定してはならない。

状態を以下で管理する。

S = (u,p)

- u：USERの位置
- p：NPCの位置

状態空間は最大でN×(N-1)。

各ターンはユーザーが先に行動し、その後NPCが行動する。

### 6-1. 探索の考え方

ユーザーは勝利につながる移動先を選択する。

NPCはユーザーの選択に対して、最もユーザーに不利な応答を選択する。

つまり、

- ユーザー側は存在する1つの勝利手順を探す。
- NPC側はすべての応答候補を検証する。
- NPCのどの応答を選んでも勝てる場合のみ、その状態を勝利可能とする。

後退解析（Attractor計算）または同等の正確なゲーム木探索を実装する。

### 6-2. 逃走者モードの勝利条件

初期の勝利集合：

W0 = { (u,p) | u = GOAL }

ユーザーが移動してゴールに到達すれば即座に勝利。

次に、NPCのすべての合法な応答に対して、勝利集合に到達できる状態を追加する。

W(k+1) = W(k) ∪ {
  (u,p) |
  存在するu'があり、
  すべてのNPCの応答p'について、
  (u',p')がW(k)に含まれる
}

ただし、捕獲された状態は勝利集合に含めない。

集合が増えなくなるまで計算する。

### 6-3. 追跡者モードの勝利条件

初期の勝利集合：

W0 = { (u,p) | u = p }

ユーザーがNPCの現在位置へ移動した時点で捕獲成功。

NPCがゴールへ到達した状態は敗北として扱う。

同様に後退解析を行い、NPCがどのように逃走しても捕獲できる状態を計算する。

### 6-4. 最小勝利手数

初期状態が初めて勝利集合に含まれた反復回数を最小勝利手数Dとする。

Dは、NPCが最善の妨害をした場合でも、ユーザーが勝利を保証できる最小ターン数とする。

勝利集合に含まれない場合は勝利保証なしとする。

D = Infinity 相当の状態は採用禁止。

探索時にはメモ化などを使用し、同一状態を繰り返し計算しない。

### 6-5. 難易度条件

設定値：

- K：最低勝利手数
- Kmax：最大勝利手数

採用条件：

K <= D <= Kmax

例えばK=8、Kmax=12なら、理論上8～12手必要な初期配置だけを採用する。

この値はゲーム開始時の初期状態に対する値とする。

## 7. NPC AI

NPCの実際の行動は、設定によって変更可能にする。

### 追跡AI

基本動作：

- ユーザーとのグラフ距離を計算する。
- 距離を短縮するノードへ移動する。
- 同じ評価値の候補が複数ある場合はランダムに選択する。

### 逃走AI

基本動作：

- ゴールとの距離を計算する。
- ゴールに近づくノードを優先する。
- ユーザーからの距離も評価する。
- 捕獲される可能性のある移動先を避ける。

### NPCの行動レベル

1. 距離優先：最短距離だけで判断する。
2. 回避型：相手との距離と次の移動候補を考慮する。
3. 予測型：相手の次の行動を予測して移動する。

GameSolverの理論上の最善手探索と、NPCControllerの実際の行動は分離すること。

NPCの実際のAIが弱いことを理由に、マップの勝利保証を成立したと判定してはならない。

## 8. 描画

HTML内にSVGを生成してマップを描画する。

画像ファイルは一切使用しない。

描画対象：

- 通路：線
- 通常ノード：黒またはグレーの円
- USER：青色の円
- NPC：赤色の円
- GOAL：黄色の円
- 移動可能ノード：強調表示

ノードの座標はJavaScriptで生成する。

各ノードをクリックすると、そのノードへの移動を試みる。

ただし、現在位置と通路で接続されているノード以外には移動できない。

SVGの表示サイズはブラウザ画面に合わせて調整する。

## 9. UI・操作画面

画面は以下の構成とする。

### 設定エリア

- ノード最小数
- リング数
- 放射方向数
- 斜め接続確率
- プレイヤーの役割
- NPCのAIレベル
- 最低勝利手数K
- 最大勝利手数Kmax
- マップ生成ボタン

### ゲームエリア

- 蜘蛛の巣型マップ
- USERの位置
- NPCの位置
- GOALの位置
- 移動可能ノードの強調表示

### 情報エリア

- 現在のターン数
- USERの位置
- NPCの位置
- USERとNPCの距離
- GOALまでの距離
- 理論上の最小勝利手数
- 現在のゲーム状態

### 操作ボタン

- 新しいマップを生成
- リスタート
- 1手戻す（可能であれば）
- NPCの行動ログ表示

## 10. ログ・デバッグ機能

以下の情報を確認できるようにする。

- 生成されたノード数
- 通路数
- 各ノードの次数
- 初期配置
- 初期配置の最短距離
- ゲーム木の探索状態数
- 勝利可能性
- 最小勝利手数
- マップ生成の試行回数
- NPCが選択した移動先と判断理由

デバッグ情報は通常のゲーム画面とは分離して、開閉できるようにする。

## 11. 生成処理の制限

ランダム生成に無限ループが発生しないようにする。

最大生成試行回数を設定する。

初期値は1000回。

1000回以内に条件を満たすマップが生成できなければ、エラー内容と生成条件を画面に表示する。

難易度条件が厳しすぎる場合は、自動的に条件を緩和せず、ユーザーに知らせる。

## 12. テスト・検証

以下のテストを実施する。

1. 最小ノード数を満たさないマップが採用されない。
2. 孤立ノードが採用されない。
3. 次数1以下のノードが採用されない。
4. USER、NPC、GOALが重複配置されない。
5. 隣接していないノードへ移動できない。
6. USERがゴールに到達すると勝利する。
7. NPCに捕獲されると敗北する。
8. NPCがゴールに到達すると逃走成功になる。
9. 初手で回避不能な捕獲が発生する配置が採用されない。
10. 勝利保証がない配置が採用されない。
11. 指定されたK～Kmaxの範囲に最小勝利手数が収まる。
12. 追跡者モードと逃走者モードの両方で勝敗判定が正しい。
13. 同じシード値で同じマップを再現できる。
14. ゲーム終了後に不正な移動ができない。

GameSolverについては、小さな手動作成グラフを用いた単体テストも実施する。

## 13. 実装の進め方

一度にすべてを実装せず、以下の順序で開発する。

第1段階：
蜘蛛の巣型グラフ生成、検証、SVG描画。

第2段階：
ユーザーとNPCの配置、基本移動、ターン進行。

第3段階：
追跡AIと逃走AI、勝敗判定。

第4段階：
GameSolverによる勝利保証と最小勝利手数の計算。

第5段階：
難易度条件を満たす初期配置の自動選別。

第6段階：
UI、ログ、デバッグ機能、テスト。

各段階で動作確認してから次に進む。

## 14. 最重要の開発方針

- まず動作するものを作る。
- 外部依存を増やさない。
- 初期バージョンはindex.htmlの1ファイルに収める。
- 数学的な勝利保証と実際のNPC AIを混同しない。
- 勝利保証のないマップを採用しない。
- 難易度は最短距離ではなく、ゲーム木探索による最小勝利手数で評価する。
- コードの可読性と機能ごとの分離を維持する。
- 未実装機能を実装済みとして扱わない。

最終成果物は、ブラウザで直接開いて遊べるindex.htmlとする。
